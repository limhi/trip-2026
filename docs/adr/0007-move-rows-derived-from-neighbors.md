# 0007 移動列的長度由路線查詢決定，改景點時間時整天連動，並移除 `drive`

日期：2026-10-30；補充決策：2026-11-01｜狀態：基礎功能已實作（v2.6）；下方「既有斷點的處理」已實作並完成整合驗收。基礎功能取代先前「改結束邊、第一項開始可改、中間開始唯讀」的版本。

## 背景

> **2026-11-02 補充決策，待實作**：每日出發／結束時間與提醒項目將採用下方「每日邊界與提醒項目」；它調整既有「所有完整時間項目含 notice 均參與」的範圍。既有程式目前仍依 2026-11-01 規則運作。

行程裡有兩種手寫的交通列（`drive`、`move`），時間各自手填，改景點時間時要自己去改前後的交通列，常常漏改。使用者的使用情境是：順序排好後，系統自動建立並更新景點之間的移動時間（已有的路線查詢功能），使用者只調整某個景點的停留時間，整天行程就連動；需要緩衝時，調單一移動的預估，或直接加長景點停留。

第一版曾決定「移動列時間由前後景點反推」，使用者試用後指出方向相反（移動時間應固定、景點時間變動時後面順延），同日改為下面的決定；第一版的 `deriveMoves` 時間規則與 `sync-moves.js` 的時間同步因此捨棄。

## 決定

- 移除 `drive` 類型，只留 `move`（驗證遇到 `drive` 報錯並提示改用 `move`，與 `duration` 改名 `note` 同一做法）；外觀統一用淺灰列。
- 移動列長度 = 預估時間（查詢時間 × 路況係數，四捨五入到分鐘）+ `buffer`（整數分鐘，可為負，預設 0，0 不寫入資料）＝排定時間。沒有路線查詢結果時維持現有長度並警告。路線重算後長度更新並連動後面。
- 資料仍存每個項目的起訖 `time`（公開頁面與排定不足比對照舊讀它；起迄時間以排定為準，不從預估推算）。時間軸永遠接得起來：每個項目的結束 = 下一個項目的開始。景點的停留自訂；移動的長度 = 預估時間 + 緩衝（只記總加減分鐘）。
- **聯動**（每個項目有開始邊與結束邊）：被改的那一邊動，那一邊之外的所有項目整段平移，項目另一邊不動。改結束邊平移後面全部，改開始邊平移前面全部；整天第一項的開始也會隨之改變，沒有固定的整天起點，也沒有「中間項目開始唯讀」。景點直接改邊的時間；移動列的邊不直接輸入，而是設緩衝並選「向前」（開始邊動）或「向後」（結束邊動），方向只決定這次往哪邊傳，不存檔。路線重算後長度變了，預設向後傳。
- **伸縮**：與聯動相同的操作，但只影響緊鄰的「移動 + 景點」：景點的伸縮是移動長度不變、鄰近的移動平移、再外一個景點只動靠近的那一邊；移動的伸縮是在某一邊設緩衝，由那一邊的鄰近景點吸收。一次性、等於兩次聯動疊加，每次單次選聯動或伸縮（欄位旁各有按鈕），不存模式。鄰近景點停留會變成 0 以下時整個操作不套用並提示。
- 時間不是完整區間的項目不平移，不做「固定時間」功能。
- 移動列的 `time` 在編輯器唯讀；`text`、`note`、`buffer` 可編輯。相鄰標記之間沒有移動列時自動補一個（`text` 預設「前一站 ➔ 下一站」）；只補不刪，多餘的只警告。
- 載入或遷移時不自動改現有時間；每天提供「整天重排」按鈕，由使用者按了才依預估時間重排整天。
- 排定不足（排定 < 預估）的紅字保留；因為移動長度由預估時間決定，只有 `buffer` 為負才會出現。公開頁面的自動連接列保留作備援。
- 編輯器的連動／伸縮先「暫時套用」（結果顯示在清單與預覽），按「確認」才生效、按「還原」回到操作前（使用者驗收後的決定，見 DESIGN 第 14.6 節）。

## 每日邊界與提醒項目（2026-11-02 已確認、待實作）

- 每天在每日設定獨立設定一個出發時間與一個結束時間。起點顯示出發時間；結束時間對應最後一個非 `notice` 項目的結束，後續 `notice` 不影響每日結束。原本時間不完整的最後入住／抵達可用單一結束時間點；已有完整區間的最後項目保留原區間。
- 修改任一每日邊界只使用**連動**：其他有時間的項目和另一邊界全部平移相同分鐘數，保留原有長度與空檔；不提供每日邊界的伸縮。先預覽、確認或**還原**；任何時間超出當天 00:00–23:59 時整次拒絕且資料不變。新增時只給值、不移動其他項目；使用者表示新增情境不會發生，暫不展開設計。
- 所有 `notice` 不佔行程時間、不參與連動；原有時間欄位移除，不把舊時間轉寫進文案。原有地點仍保留地圖標記、導航與路線。文案仍只供閱讀，不作時間計算依據。
- 除每日起點／終點時間點及 `notice` 外，行程項目需要明確的完整起訖時間；擇一組維持共用時間。缺少明確時間時可以存草稿，但阻擋發布；空檔照舊提示而不擋發布。
- 既有非起點／終點、沒有完整時間的項目轉為 `notice`；原本不完整的最後入住或抵達轉為明確結束時間點。Day 4 新增 18:30 終點；Day 6 最後項目保留 15:03–15:33。Day 3 既有 `notice` 的 15:23–15:43 移除。上述資料變更尚未執行，六天確認值與注意事項見 `docs/TODO.md`。
- 不採邊界伸縮，因為使用者希望整天其他項目直接平移；不把未定事項偽裝成有停留的項目，因為提醒不應牽動行程。此次不據文案推算時間。

## 後果

### 既有斷點的處理（2026-11-01 已實作）

發現：Day 1 移動為 `07:10 - 09:00`，蠟筆城堡為 `09:40 - 11:20`，相隔 40 分鐘。修正前的連動只按新舊時間差平移，會保留原有空檔，與「時間相接」的設計目標不符；修正前的檢查也沒有偵測此類斷點。

- **時間依據**：只使用結構化的 `time`、路線快取、路況係數與 `buffer`。`desc`、`text`、`note` 等文案僅供閱讀，不解析其中的時間，不據以排程；文案正確性留待最後人工檢查。
- **參與範圍**：所有具有完整時間區間的項目都參與銜接，不依類型或是否有地點篩選；擇一組視為一站。沒有完整時間區間（如「17:10 後」）的項目跳過、不改動。
- **連動**：以使用者確認的開始邊或結束邊為準，接齊操作側相鄰項目的邊界；維持移動的「預估＋緩衝」長度，向該側回推或順推，並依原有連動規則平移該側其他項目。未涉及的斷點仍警告，不藉此重排整天。
- **伸縮**：同樣接齊操作側邊界，只由緊鄰的移動與景點吸收變更；無法吸收（例如景點停留變成 0 以下）就整次不套用並提示。既有超出當天等拒絕條件保留。
- **相同值仍修正**：開始或結束時間即使與原值相同，按下連動／伸縮仍須檢查並修正該側斷點，不能因時間差為 0 就直接返回。操作沿用暫時套用、確認、還原；還原須完整回復操作前資料。
- **既有資料**：載入時只提示空檔或重疊，不自動修正。警告列出哪一天、相鄰項目、時間與相差分鐘數；編輯器載入／存檔／發布檢查及 `tools/check.js` 應能提示，仍允許存檔、發布，檢查不因斷點失敗。
- **整天修正**：沿用「整天重排」，固定第一個完整時間項目的開始，維持各項停留長度，移動使用預估＋緩衝（無快取沿用現有長度並警告）；先預覽，確認才生效，還原可完整復原。不增加中間錨點選擇。
- **本次範圍**：只落實程式與驗收，不預先修改任何行程資料。保留 Day 1 的 40 分鐘空檔，用來驗證警告、原值操作接齊、預覽確認與還原；其他天也不自動重排。這項決定取代討論中曾同意的「本次直接修正 Day 1」。

取捨：不採載入時自動接齊或每次編輯重排整天，避免默默改變其他安排；代價是尚未明確操作修正的資料仍可能有斷點，因此必須提供不阻擋發布的警告。實作與驗收清單見 [TODO](../TODO.md#時間銜接修正2026-11-01)。

### 基礎功能的後果

- 好處：改一個景點的停留，整天自動順延；移動時間與預估時間一致；緩衝集中在單一移動，路線重算後仍有效。
- 代價：連動是編輯器的操作，直接改 JSON 的人（或 AI）要自己平移後面的時間（或請編輯器「整天重排」）；移動長度依賴路線快取，還沒算路線時只能警告；沒有固定時間的項目，餐廳預約這類要用不完整時間（如「後」）或事後手調。

## 考慮過的其他做法

- 移動列時間由前後景點反推（第一版）：景點時間固定、移動列吸收差額，與使用者「移動時間固定、後面順延」的想像相反。
- 直接覆寫移動總長度：路線重算後覆寫值會與查詢結果脫鉤。
- 推導值不存、渲染時才算：公開頁面、路段規則與排定時間計算都要改，`time` 欄位名存實亡。
- 保留 `drive` 作為「可手調時間」的交通列：兩種類型並存，規則要分兩套。
- 載入時自動重排：一上線就會把整份既有行程的時間全部改掉。
