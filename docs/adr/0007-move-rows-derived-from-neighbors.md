# 0007 移動列的時間由前後標記推導，並移除 `drive`

日期：2026-10-30｜狀態：已決定，尚未實作

## 背景

行程裡有兩種手寫的交通列（`drive`、`move`），時間各自手填，改景點時間時要自己去改前後的交通列，常常忘記；相鄰標記之間沒有交通列時，公開頁面只能補唯讀的連接列。使用者不再使用 `drive`，也希望調整景點時間時，移動列的時間自動跟著變，不讓人手調。

## 決定

- 移除 `drive` 類型，只留 `move`（驗證遇到 `drive` 報錯並提示改用 `move`，與 `duration` 改名 `note` 同一做法）；外觀統一用現有 `move` 的淺灰列。
- `move` 的 `time` = 前一個地圖標記的結束時間 − 下一個標記的開始時間；只在兩端都是完整區間、兩標記之間恰好一個 `move` 時推導；擇一組用共用時間框。推導值**存進** `data/trip.json`，公開頁面與路段規則照舊讀 `time`。
- 兩端重疊（下一個開始早於上一個結束）時 `time` 清空並警告；其中一端不是完整區間時保留現有 `time`。
- 編輯器：`move` 的 `time` 唯讀，`text`、`note` 可編；相鄰標記之間沒有 `move` 時自動補一個（`text` 預設「前一站 ➔ 下一站」）；**只補不刪**，多餘的只警告。
- `check.js` 發現 `time` 與推導值不一致只印警告；`node tools/sync-moves.js` 一次同步。公開頁面的自動連接列保留作備援。
- 現有資料遷移：先暫存 13 筆 `drive`／`move` 的 `text`、`note`，全部刪掉並依規則重建，再把文字與備註補回對應位置，補不回的逐筆請使用者確認。

## 後果

- 好處：改景點時間就同步前後移動列，「排定時間」與「排定不足」不再因漏改而失真；類型少一種，編輯器與樣式更簡單。
- 代價：推導值存進資料，AI 或人直接改 JSON 後必須同步（用 `sync-moves.js`），否則只會被警告；手寫的移動時間不再被保留；只補不刪，多餘的列要人處理。

## 考慮過的其他做法

- 推導值不存、渲染時才算：資料不會不一致，但公開頁面、路段規則與排定時間計算都要改成讀推導值，`time` 欄位名存實亡。
- 保留 `drive` 作為「可手調時間」的交通列：兩種類型長期並存，規則要分兩套。
- 刪除多餘的移動列：會誤刪使用者手寫的 `text`。
