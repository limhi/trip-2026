# 0007 移動列的長度由路線查詢決定，改景點時間時整天連動，並移除 `drive`

日期：2026-10-30｜狀態：已實作（v2.6）；`drive` 移除、自動補移動列、緩衝欄位、整天重排、邊界連動與伸縮都已完成，取代先前「改結束邊、第一項開始可改、中間開始唯讀」的版本

## 背景

行程裡有兩種手寫的交通列（`drive`、`move`），時間各自手填，改景點時間時要自己去改前後的交通列，常常漏改。使用者的使用情境是：順序排好後，系統自動建立並更新景點之間的移動時間（已有的路線查詢功能），使用者只調整某個景點的停留時間，整天行程就連動；需要緩衝時，調單一移動的預估，或直接加長景點停留。

第一版曾決定「移動列時間由前後景點反推」，使用者試用後指出方向相反（移動時間應固定、景點時間變動時後面順延），同日改為下面的決定；第一版的 `deriveMoves` 時間規則與 `sync-moves.js` 的時間同步因此捨棄。

## 決定

- 移除 `drive` 類型，只留 `move`（驗證遇到 `drive` 報錯並提示改用 `move`，與 `duration` 改名 `note` 同一做法）；外觀統一用淺灰列。
- 移動列長度 = 預估時間（查詢時間 × 路況係數，四捨五入到分鐘）+ `buffer`（整數分鐘，可為負，預設 0，0 不寫入資料）＝排定時間。沒有路線查詢結果時維持現有長度並警告。路線重算後長度更新並連動後面。
- 資料仍存每個項目的起訖 `time`（公開頁面與排定不足比對照舊讀它；起迄時間以排定為準，不從預估推算）。時間軸永遠接得起來：每個項目的結束 = 下一個項目的開始。景點的停留自訂；移動的長度 = 預估時間 + 緩衝（只記總加減分鐘）。
- **聯動**（每個項目有開始邊與結束邊）：被改的那一邊動，那一邊之外的所有項目整段平移，項目另一邊不動。改結束邊平移後面全部，改開始邊平移前面全部；整天第一項的開始也會隨之改變，沒有固定的整天起點，也沒有「中間項目開始唯讀」。景點直接改邊的時間；移動列的邊不直接輸入，而是設緩衝並選「向前」（開始邊動）或「向後」（結束邊動），方向只決定這次往哪邊傳，不存檔。路線重算後長度變了，預設向後傳。
- **伸縮**：與聯動相同的操作，但只影響緊鄰的「移動 + 景點」：景點的伸縮是移動長度不變、鄰近的移動平移、再外一個景點只動靠近的那一邊；移動的伸縮是在某一邊設緩衝，由那一邊的鄰近景點吸收。一次性、等於兩次聯動疊加，每次單次選聯動或伸縮（欄位旁各有按鈕），不存模式。鄰近景點停留會變成 0 以下時整個操作不套用並提示。
- 時間不是完整區間的項目不平移，不做「固定時間」功能。
- 移動列的 `time` 在編輯器唯讀；`text`、`note`、`buffer` 可編輯。相鄰標記之間沒有移動列時自動補一個（`text` 預設「前一站 ➔ 下一站」）；只補不刪，多餘的只警告。
- 載入或遷移時不自動改現有時間；每天提供「整天重排」按鈕，由使用者按了才依預估時間重排整天。
- 排定不足（排定 < 預估）的紅字保留；因為移動長度由預估時間決定，只有 `buffer` 為負才會出現。公開頁面的自動連接列保留作備援。
- 編輯器的連動／伸縮先「暫時套用」（結果顯示在清單與預覽），按「確認」才生效、按「還原」回到操作前（使用者驗收後的決定，見 DESIGN 第 14.6 節）。

## 後果

- 好處：改一個景點的停留，整天自動順延；移動時間與預估時間一致；緩衝集中在單一移動，路線重算後仍有效。
- 代價：連動是編輯器的操作，直接改 JSON 的人（或 AI）要自己平移後面的時間（或請編輯器「整天重排」）；移動長度依賴路線快取，還沒算路線時只能警告；沒有固定時間的項目，餐廳預約這類要用不完整時間（如「後」）或事後手調。

## 考慮過的其他做法

- 移動列時間由前後景點反推（第一版）：景點時間固定、移動列吸收差額，與使用者「移動時間固定、後面順延」的想像相反。
- 直接覆寫移動總長度：路線重算後覆寫值會與查詢結果脫鉤。
- 推導值不存、渲染時才算：公開頁面、路段規則與排定時間計算都要改，`time` 欄位名存實亡。
- 保留 `drive` 作為「可手調時間」的交通列：兩種類型並存，規則要分兩套。
- 載入時自動重排：一上線就會把整份既有行程的時間全部改掉。
